5. 它实际解决了哪些正确性问题

5.0 四个动作，不是一回事

动作物理效果语义何时用
retract正文保留，账本新增撤回事实，进入 quarantined停止使用，保留证据怀疑记忆错误，先别喂给模型
restore只解除本次收据观察到的撤回 token恢复可见，但不抹掉撤回历史核对后确认可继续使用
revert一个事务内恢复旧快照、删目标、提交收据物理撤销某次写入那次写入本身不该发生
delete行消失，账本事件仍在管理面数据删除用户要求删除数据；不是审阅动作

隔离、物理删除、更正不是等价概念。未来信念维护模型应把 “撤回错误断言”和“追加更正断言”分开，而不是把 revert 当时间旅行。

5.2 Token 语义：恢复只取消它观察到的撤回

retract R1 → +T1 restore R2 → observed={T1}，只取消 T1 retract R3 → +T2（已隔离也独立生效） R2 迟到重试 → 仍只取消 T1 → 记忆保持 quarantined

这是为了避免迟到的 restore 覆盖更新的 retract。 每个新 retract 独立产生 token；restore 的收据固定 observed 集合。

  • 血缘缺失时保守隔离并标 lineage_incomplete，不伪装完整分析。
  • 图预算：50k 节点 / 500k 事件 / 64MiB，超限拒绝。

5.4 Clear 代次栅栏：不靠时钟

SQLite/Mongo 在事务中提交单调 guard_epoch；抽取开始时捕获 review_epoch。 clear 之后迟到的旧代次写入被识别并隔离，无法靠“看起来更新”的时间戳复活。 clear: 与 revert: 类 token 不能被普通 restore 取消。

5.5 revert：三段式物理撤销

1计划

2事务
恢复快照 + 删除目标 + 提交收据；任一失败整体回滚。
3镜像
收据发布 outbox；失败如实标 outbox_pending。
守卫行为
目标之后有更新写入409；先撤更新层或 force

6. 关键缺口：变更链有，使用链没有

issue #1615 的核心缺口仍然真实存在

PR #1538 可以回答“一条记录被哪些写入/替换/审阅事件改过”， 但不能回答“它进入过哪些生成上下文、影响了哪些回答、间接生成了哪些新记忆”。

6.1 L1 generation-log 仍只记录 L0 输入

它只能回答“这次 L1 抽取消费了哪些对话消息”，不能回答“当时上下文里注入了哪些 L1 记忆”。

7. 对重新设计的含义

值得保留
变更事实基座：MemoryEvent、账本存储、事务提交、clear epoch、写入链接入、核心测试。
单独评估
运维恢复：outbox、replay、redaction、health、migration/export，不与追溯链捆绑。
需要重建
审阅动作面：retract/restore/revert/derived 的语义和 API，应按新信念模型重设计。

两条新契约比“某一层修对”更根本

1进库必带理由
无论抽取、直写、导入、seed 还是迁移，写入任何层的断言都必须显式声明理由来源。
2入 context 必留痕
召回、工具注入、skill、MMD、prependContext 都必须记录“哪一版内容进入了哪次生成”。
3更正而非时间旅行
错误信念的处理应是“撤回旧断言 + 追加可过期的新断言”，不是伪装删除过去。

最小落地顺序建议

顺序工作目的
①定义“断言 + 理由/版本”的数据模型先决定追溯契约，再决定保留哪些实现

③建立 generation-context ↔ L0 message ↔ extraction 的关联键闭合 A → response → B 中间两跳
④做只读反向查询/影响报告先给出 bounded blast radius，再谈自动隔离
